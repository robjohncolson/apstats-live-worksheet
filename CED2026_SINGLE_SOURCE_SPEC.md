# CED-2026 numbering: one source, old keys never printed (spec)

Status: approved 2026-10-12 (teacher: "how do we get rid of this once and for all, across
curriculum_render and this repo?" → "Go for it"). Built overnight: Opus 5.5 implements, Codex
(gpt-6-astra) reviews, then commit + push in both repos.

## The problem

Every stored thing is keyed by the OLD 9-unit lesson id (`3.5`): worksheet/prompt/Blooket/tutor file
names, cr Supabase answers (`WS-U3L5-Q7`), roster `item_ledger` keys (`FA:3.5`, `BL:3.1`), Supabase
`lesson_urls.topic`, student localStorage, cr `curriculum.js`, Schoology column titles ("3.1 Blooket").
Students see the NEW CED-2026 names on the Desk calendar ("1.13 · Experimental Design") but the old key
leaks into other surfaces (gradebook columns, Schoology, tile headers "old 3.5", cr quiz headings), so
"3.1 Blooket" cannot be found on a calendar that only says 1.10–1.13. Worse, the two repos each carry
their own crosswalk and they have DRIFTED: `follow-alongs/2026-crosswalk.json` says old 3.6's
simulation segment is `bonus`; `curriculum_render/data/2026-crosswalk.json` still says `core 1.13`.

## Decision

The old key stays the storage/primary key (renaming it mid-year means rewriting three schemas, ~300
file names, bookmarked URLs and Schoology history). It becomes **opaque**: one crosswalk, vendored;
every human-facing string goes through the label function; a guard test in each repo keeps it that way.

## 1. One crosswalk, vendored (follow-alongs → curriculum_render)

- `follow-alongs/2026-crosswalk.json` is the single source. `scripts/sync-ced-crosswalk.mjs` copies it
  to `curriculum_render/data/2026-crosswalk.json` (and anywhere else cr reads it), exactly like
  `scripts/sync-park-calculator.mjs`. A test in EACH repo asserts the copies are byte-identical with the
  source (cr's test reads the sibling repo when present, else skips with a clear message).
- `curriculum_render/js/sy2627_overlay.js` keeps its logic but takes ALL data from the vendored file:
  no hard-coded unit labels or topic buckets that could disagree with the crosswalk. The relay
  (`railway-server/frameworks.js`) likewise.
- A shared Node-and-browser label helper, `follow-alongs/lib/ced-label.js` (UMD-style: works as a
  `<script>`, in Node `require`, and in ESM via `lib/ced-label.mjs` re-export), derived from the
  existing `js/ced2026-labels.js` logic: `cedTopicLabel(oldKey) → { topic: '1.13', text: '1.13 ·
  Experimental Design', unit: 1, status: 'core'|'bonus' }`, plus `cedColumnTitle(kind, oldKey)` →
  `'1.13 Follow-Along'`, `'1.10 Blooket'`, `'1.13 Quiz'`, `'Unit 1 Progress Check'`. Combined keys
  (`3.6-7`, `4.1-2`) and bonus topics follow the rules already in `js/ced2026-labels.js`.
  The Desk's existing `cedLabel()` delegates to it (no behaviour change on the calendar).

## 2. Old keys never printed

Every surface below renders the CED label; the old key may appear only in `data-*` attributes, ids,
URLs and tooltips of the form "stored as 3.5":
- roster-server `gradebook-grid.js` column titles (`title`), Do Now / missing-work rows, the in-app
  1:1 gradebook, teacher dashboard, class snapshot, pacing overview, coach lines.
- Desk tile headers: "1.13 · Experimental Design · Day 1 — CED Unit 1 (old 3.5: video 'Unit 3 Lesson
  5', worksheet u3_lesson5)" → "1.13 · Experimental Design · Day 1" with the video/worksheet names in
  the links only.
- curriculum_render quiz UI: headings, unit pickers, result pages, peer-data labels.
- Schoology sync (`tools/schoology_sync_lib.assignment_title`): see §3.
Columns gain a second field `schoologyTitle`: the title the real Schoology column has TODAY (old
style until §3's rename runs), so the "Schoology: <column>" tag on missing-work rows keeps naming the
column a student will actually find in Schoology. One constant flips it: `SCHOOLOGY_TITLES_CED`
(roster `grade-config.js`, default `false`) — set `true` the day the rename runs.

## 3. Schoology one-time rename (teacher-run, prepared tonight)

- `tools/schoology_rename_columns.py`: dry-run by default; prints a plan "3.1 Blooket → 1.10 Blooket"
  per section from the same `cedColumnTitle` map (python port in `schoology_sync_lib`, tested against
  the JS helper via a shared fixture `data/ced-column-titles.json` generated by the JS and read by both),
  `--apply` renames via the existing CDP rig. Columns it cannot find are listed, never created.
- `assignment_title(kind, key, ced=SCHOOLOGY_TITLES_CED)`: with `ced=False` (today) it produces the
  OLD titles exactly as before (every existing python test still passes unchanged); with `ced=True` it
  produces the CED titles. The daily sync reads the flag from `tools/schoology_sync_config.json`.
- Order on rename day (teacher): run `schoology_rename_columns.py --apply` → set the python flag → set
  roster `SCHOOLOGY_TITLES_CED=true` → redeploy. Best-wins is unaffected (scores never move).

## 4. Guard tests (what makes it permanent)

- follow-alongs: `tests/ced-no-raw-keys.test.js` renders the Desk's student-facing strings (tile
  header, Do Now, missing-work rows, gradebook column titles from `gradebook-grid.js`, coach panel)
  through the existing jsdom harnesses and asserts no `\b[1-9]\.\d{1,2}\b` old key that is not the
  CED topic of that lesson appears in text content. Known-safe literals (dates, percentages, "1.5 IQR",
  version strings) are excluded by context, not by allow-listing numbers.
- curriculum_render: `tests/ced-no-raw-keys.test.js` for the quiz UI headings + a crosswalk
  byte-identity test.
- Both: a test that every core entry of the crosswalk maps to exactly one CED topic and every lesson in
  `data/lesson-schedule.json` has a crosswalk entry (no silent fallthrough to the old key).

## Out of scope (deliberately)

Renaming files, question ids, ledger keys, `lesson_urls.topic`, `curriculum.js`, or the schedule's
`lessons[].unit`. Student bookmarks and history keep working. A future summer may retire the old key
once no live data references it; nothing here blocks that.
