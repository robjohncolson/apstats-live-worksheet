## Bug classes to check for

### Phase 2 — Chart rendering lift

- [ ] **Namespace collisions**: the lifted `curriculum-charts.js` creates `window.charts = window.charts || {}`, `window.chartInstances = window.chartInstances || {}`, `window.getChartHtml`, `window.renderChartNow`, plus any helper globals from `charthelper.js`. Grep for these names in `study_guide_diagnostic.html` — are there any pre-existing definitions that get clobbered or clobber the lifted code?
- [ ] **Script load order**: the 3 new script tags (`chart.min.js`, `chartjs-plugin-datalabels.min.js`, `curriculum-charts.js`) must load BEFORE the main IIFE executes `attachMedia`. Check the script tag order in the HTML. Also check: is Chart.js loaded before its plugin? The plugin auto-registers on load and requires Chart to exist.
- [ ] **`generateChartColors` dependency**: the original `curriculum_render/js/charts.js` references `generateChartColors(count)`. Sonnet's result says `charthelper.js` was combined into `curriculum-charts.js`. Verify `generateChartColors` is actually present in the lifted file — grep for it in `lib/curriculum-charts.js`. If missing, chart rendering will throw at runtime for bar/histogram types.
- [ ] **`requestAnimationFrame` timing**: the integration pattern uses `requestAnimationFrame(() => renderChartNow(...))` to defer the render until after the canvas is in the DOM. But if `attachMedia`'s caller does NOT synchronously append the returned `wrap` to the DOM before the next frame, `renderChartNow` will call `document.getElementById(canvasId)` and get null. Check: are there any `attachMedia` callers that build the wrap but don't immediately append? The existing callers (around line 4072) should append synchronously, but verify.
- [ ] **`chartCounter` scope**: the counter must be module-scoped (inside the main IIFE) so it persists across `attachMedia` calls without leaking to `window`. Verify it's declared inside the IIFE, not at the top of the file.
- [ ] **Chart cleanup on re-render**: when the active probe changes, the old chart's canvas is removed from the DOM. `renderChartNow` destroys existing chart instances before creating new ones via `window.chartInstances[canvasId].destroy()`. But if the counter increments each time, old canvas IDs are orphaned in `chartInstances` — a memory leak. Check: does anything prune `chartInstances`? Is there a risk of the map growing unbounded in a long session?
- [ ] **Mixed attachments**: what happens when a question has BOTH a table AND a chart (or image + chart)? The extended `attachMedia` should render all three. Verify the three branches don't short-circuit each other.
- [ ] **Missing `chartConfig`**: some chart attachments in curriculum.js have `chartConfig` with `xAxis`/`yAxis`/`gridLines`; others don't. `getChartHtml` uses `chartData.chartConfig || {}`. Check that the lifted code handles missing config gracefully for all 9 chart types (scatter, histogram, bar, dotplot, boxplot, numberline, pie, normal, chisquare).
- [ ] **Unsupported chart types in curriculum.js**: the audit says 9 chart types exist. Does `curriculum-charts.js` actually handle all 9? `normal` and `chisquare` are statistical distributions, not standard Chart.js types — verify the lifted code has renderers for them.
