## Bug classes to check for

### Workstream A — Login bar UX

- [ ] **Event-handler leaks**: `refreshAuthPanelVisibility` replaces `.student-info` innerHTML when signing in, and restores it when signing out. Check that the sign-out path **re-attaches** event handlers to the restored form elements (login button click, password Enter key, username change, create link click). A common bug: replacing innerHTML destroys the original DOM nodes and all their listeners. The restored `#studentLoginBtn` etc. might be new nodes without any wired handlers. Look for: does the restore path re-query `ui.loginBtn` etc. and re-bind, or does it rely on the original references (which now point to orphaned nodes)?
- [ ] **`ui` object staleness**: the `ui` object (around line 1897+) caches DOM element references. If `refreshAuthPanelVisibility` reassigns `.student-info` innerHTML, the cached references in `ui` become stale. Check if there's a re-cache step.
- [ ] **Username dropdown change handler**: when a signed-in user changes the username selector, auth should be cleared. Verify the handler is added **once** at init and **not** re-added each time `refreshAuthPanelVisibility` runs (double-binding).
- [ ] **Modal open state race**: if the user clicks the create link twice rapidly, or clicks while typing, does the modal state get confused? Check the `showCreateUserModal` / `hideCreateUserModal` pair for idempotency.
- [ ] **`state.studentPeriod` drift**: the plan says keep the field in state for backwards compat but stop capturing. Verify no code path still writes to `state.studentPeriod` (would be a dead write). Verify no code path still **reads** `state.studentPeriod` and errors on missing values.
- [ ] **Escape key double handler**: if the modal adds an Escape handler on keydown, is there a global Escape handler for other modals (mastery map, formula card)? Are they layered correctly so each modal only eats its own Esc?
- [ ] **Tab order / accessibility**: after the restructure, does tabbing from username → password → Sign In work naturally? Create link should be tab-reachable.

### Workstream D — Rubric surfacing in `renderGrade`

- [ ] **Graceful degradation**: if `STUDY_GUIDE_FRQ_BANK[questionId]` is null, or if `bankEntry.solution` is missing, or if `bankEntry.solution.scoring.rubric` is missing, does `renderGrade` still work? The plan requires graceful skip of the rubric `<details>` in each case.
- [ ] **Shape variance**: the FRQ bank has **two rubric styles**. U1 has detailed `scoringNotes` on each rubric part. U2 has a simpler rubric without `scoringNotes` on some parts. Check the render code handles both shapes — missing `scoringNotes` should not throw or render `undefined` text.
- [ ] **`solution.parts` vs `solution.scoring.rubric` mismatch**: the parts array and the rubric array are separate. Verify the render code matches them by `partId`/`part` field, not by array index — some FRQs may have different lengths.
- [ ] **MathJax typeset timing**: after appending the solution body, the plan requires `window.MathJax.typesetPromise([container])`. Check that MathJax is typeset **after** the container is in the DOM, not before. And that it's guarded with `if (window.MathJax && typeof window.MathJax.typesetPromise === 'function')`.
- [ ] **`questionId` threading**: `renderGrade` signature changed to include `questionId`. Find every call site of `renderGrade` and verify each passes the right question id. The plan says there was one call site; verify.
- [ ] **Grade card re-render**: if a student grades, then appeals, then regrades, does the grade card re-render cleanly? The rubric/solution `<details>` should not accumulate or duplicate.
- [ ] **`grade.score` visibility gate**: the plan says the disclosures only render when `grade && grade.score` is truthy. Check that the grade card before-grade state (when no grade exists) doesn't show stale rubric disclosures.
- [ ] **LaTeX in `solution.parts[i].response`**: the bank has inline `\(...\)` and display `\[...\]` math. Does the renderer preserve these raw strings so MathJax can find them? A common bug: HTML-escape the solution string, which turns `\(` into `\(` literally (still OK) but turns `<` into `&lt;` which breaks nothing in this case. Make sure `response` goes through `textContent` or a safe paragraph builder, not `innerHTML` without escaping.
