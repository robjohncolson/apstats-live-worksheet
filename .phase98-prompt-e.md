# Phase 98E — Mode Buffer Populator Hunt via ISR Event Loop

## Context

TI-84 Plus CE ROM transpiler. The mode display buffer at `0xD020A6..0xD020BF` (26 bytes ASCII) is the source of the home-screen mode row text ("Normal Float Radian..."). Phase 91c confirmed the format is raw ASCII — seeding it with `'ABCDE...Z'` makes letter-shaped glyphs render correctly through `0x0a29ec`.

**Problem**: In the 100k or 500k boot snapshots, the buffer stays all `0xFF` (uninitialized). Phase 92 found three writers during OS init:
- `0x001881` zeros it (26×0x00)
- `0x00287D` resets it to 0xFF
- `0x0A17AE` writes context-specific content (Y= editor writes eqnname strings into it; for home screen callers it writes 0xFF back)

**None of those** populate it with the home-screen mode text. Phase 97A confirmed 500k boot = 100k boot (both terminate at step 691) — so the real populator is in code that runs **after** the OS init returns to HALT, i.e., in the ISR path. Phase 71 established that the OS dispatch is ISR-driven via BCALL slot 21.

**Hypothesis**: The mode text populator is reached via the hardware timer interrupt path. By running with `timerInterrupt: true`, we let the interrupt path execute, and we can trap writes to the mode buffer to find the populator's PC.

## Probe Specification

### Setup

```js
import { createExecutor } from './cpu-runtime.js';
import { createPeripheralBus } from './peripherals.js';
import { pathToFileURL, fileURLToPath } from 'node:url';
import path from 'node:path';
import fs from 'node:fs';

const __dirname = path.dirname(fileURLToPath(import.meta.url));
const romBytes = fs.readFileSync(path.join(__dirname, 'ROM.rom'));
const mod = await import(pathToFileURL(path.join(__dirname, 'ROM.transpiled.js')).href);
const BLOCKS = mod.PRELIFTED_BLOCKS;

const mem = new Uint8Array(0x1000000);  // 16MB required
mem.set(romBytes);
const peripherals = createPeripheralBus({ pllDelay: 2, timerInterrupt: true });  // KEY: timer on
const executor = createExecutor(BLOCKS, mem, { peripherals });
const cpu = executor.cpu;
```

### Phase 1 — Cold boot + OS init with timer on

```js
executor.runFrom(0x000000, 'z80', { maxSteps: 20000, maxLoopIterations: 32 });
cpu.halted = false; cpu.iff1 = 0; cpu.iff2 = 0;
cpu.sp = 0xD1A87E - 3; mem.fill(0xFF, cpu.sp, 3);
const osInit = executor.runFrom(0x08C331, 'adl', { maxSteps: 500000, maxLoopIterations: 10000 });
// osInit.steps should be 691 (same as timer=false — OS init terminates before looping)
```

Record `osInit.steps / .termination / .lastPc` and the mode buffer state after init (should be 0xFF×26).

### Phase 2 — Set up write8 trap for 0xD020A6..0xD020BF

```js
const origWrite8 = cpu.write8.bind(cpu);
const bufWrites = []; // [{step, addr, val, pc}]
let stepCounter = 0;
cpu.write8 = (addr, value) => {
  if (addr >= 0xD020A6 && addr <= 0xD020BF) {
    bufWrites.push({ step: stepCounter, addr, val: value, pc: cpu._pc || cpu.pc || -1 });
  }
  return origWrite8(addr, value);
};
```

Also trap writes to cursor bytes `0xD00595/0xD00596` and to a few mode-state bytes (`0xD00085`, `0xD0008A`) with a separate log — these are suspected state setup before the populator runs.

### Phase 3 — Try to drive the ISR path

Several options. Try each in sequence (the probe should try all and report which produced writes):

**Option A**: Re-run OS init after clearing `halted` and setting IFF1/IFF2 both to 1 (enable interrupts), with `maxSteps: 1,000,000`:

```js
cpu.halted = false; cpu.iff1 = 1; cpu.iff2 = 1;
const longRun = executor.runFrom(0x08C331, 'adl', { maxSteps: 1000000, maxLoopIterations: 20000, onBlock: () => { stepCounter++; } });
```

**Option B**: Run from the event loop entry `0x0019BE` (Phase 58 decoded this as the main event loop) with timer on:

```js
cpu.halted = false; cpu.iff1 = 1; cpu.iff2 = 1;
cpu.sp = 0xD1A87E - 3; mem.fill(0xFF, cpu.sp, 3);
const evLoop = executor.runFrom(0x0019BE, 'adl', { maxSteps: 1000000, maxLoopIterations: 20000, onBlock: () => { stepCounter++; } });
```

**Option C**: Run from the HALT recovery entry `0x0019B5` (boot halts here after OS init) — Phase 58 finding:

```js
cpu.halted = false; cpu.iff1 = 1; cpu.iff2 = 1;
const haltRec = executor.runFrom(0x0019B5, 'adl', { maxSteps: 1000000, maxLoopIterations: 20000, onBlock: () => { stepCounter++; } });
```

**Option D**: Run from alternate OS init entry `0x08c366` (state-resume, JT slot 21) with interrupts enabled:

```js
cpu.halted = false; cpu.iff1 = 1; cpu.iff2 = 1;
const resume = executor.runFrom(0x08C366, 'adl', { maxSteps: 1000000, maxLoopIterations: 20000, onBlock: () => { stepCounter++; } });
```

Between options, snapshot/restore mem from after OS init to get a clean starting state each time. Create a snapshot after Phase 1 and restore before each option.

### Phase 4 — Analysis

For each option that produced writes to the mode buffer:
- Dedupe write PC addresses (the populator function address will appear many times)
- For each unique PC, count how many bytes were written from it
- Top candidate: the PC that wrote 26 bytes of varied content (not all 0xFF, not all 0x00, not all same byte)
- Report the final buffer state after each option (as ASCII and hex)

Also check the cursor and mode-state bytes for changes — the populator probably sets them too.

### Expected outcomes

- **Best case**: One option produces a sequence of writes to `0xD020A6..BF` with ASCII chars corresponding to "Normal Float Radian       " or similar, with a clear populator PC address. That PC is the real populator function — report it prominently.
- **Partial**: Writes happen but content is still 0xFF or 0x00. Report the PCs anyway — they're closer to the populator than anything Phase 92 found.
- **Null**: Zero writes to the mode buffer in any option. Report that and the final buffer state.

### Important notes

- ISR dispatch requires `iff1=1, iff2=1, halted=false`. The Phase 27/56 sessions found that `cpu.halted` blocks progress unless cleared.
- The event loop at `0x0019BE` is transpiled (Phase 88 confirmed blocks exist), but Phase 87b found "execution loops in hardware poll at 0x690-0x69a". Timer ISR may or may not fire — depends on peripherals.js timer implementation.
- Watch for `maxSteps` being hit — if it terminates with `max_steps` instead of `halt`, that's fine; the probe is still valid.
- If `missing_block` fires early on options B/C/D, report the lastPc and move on — don't try to work around it.

### Report

Contents:
1. Phase 1 result (osInit) — steps/term/lastPc
2. Mode buffer state after OS init
3. Table of option results (A/B/C/D): steps, termination, lastPc, writes count, final buffer state (ASCII preview)
4. For each option with writes: list of unique write PCs with byte counts
5. **Verdict**: is any option the mode populator? If yes, the PC address. If no, next steps.
