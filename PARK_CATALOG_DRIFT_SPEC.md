# PARK_CATALOG_DRIFT_SPEC: the park calculator catalogue has fallen behind the schedule

Status: BRAINSTORM, for the teacher to review. Nothing here is implemented yet.
Date: 2026-11-08. Repos: follow-alongs (fa, branch master) and curriculum_render (cr, branch main).
No student data is involved. This change cannot move a grade: the park is grade-inert, and the
catalogue only decides which day a calculator skill opens.

`apstat-park/calculator-curriculum.test.mjs`.

`apstat-park/calculator-catalog.mjs` is generated data. Its unlock dates come from
`data/lesson-schedule.json`, and two schedule commits moved lessons without regenerating it:

| ae65d549 | Fri 11/06 14:07 | Period E pair days hold at most 3 videos, so E's March shifts by one meeting |
| 084d953a | Fri 11/06 23:11 | Period B poster days (Tue 11/10, Thu 11/12, Fri 11/13) push B's November and December later |

**Correction to the 11/07 note:** CI has been red since **ae65d549**, not 084d953a. The CI run for

## 2. Why the 11/07 regen looked so much worse: the catalogue is built in TWO steps

The 11/07 diagnosis ran only the generator. That rewrote about 94 route hunks (it added `DOWN` and
"Choose DOWN." steps and removed the `ALPHA` letter shortcuts) and broke six more tests. That
regen was incomplete. It does not mean the committed catalogue is stale. Since 7f047aba
(2026-10-12, the route audit), the catalogue has been built in two steps:

```
node scripts/build-park-curriculum.mjs            # writes the catalogue with the LONG routes
node scripts/audit-calculator-routes.mjs --apply  # rewrites 28 routes to the short natural path
```

The second step is documented only inside the audit script ("build-park-curriculum.mjs regenerates
the catalogue with the long routes: run --apply after it"). The catalogue's own header names only
the generator ("Generated by scripts/build-park-curriculum.mjs. Do not edit."), so anyone who
trusts that header undoes the route audit. That is the trap.

**Verified 11/08 in a scratch copy, without touching the tree:** generator, then `--apply`, gives
a catalogue whose diff against the committed one is the date-only diff above. Routes and hints are
byte-identical for all 99 problems. A second audit run reports "0 open". In that scratch copy,
`calculator-curriculum.test.mjs` passes 107/107, and `calculator-goals`, `calculator-variants`,
`calculator-srs` and `calculator-recognition` all pass. Neither engine nor generator has changed
since then. The native engine was last edited 10/10 and only moved on 10/15. The generator's only
later edit (aa5d750f) repointed paths.

### The relay mirror

cr keeps a byte-identical copy at `../curriculum_render/railway-server/apstat-park/calculator-catalog.mjs`.
Today it equals fa's committed copy, and so do all 12 shared modules in `scripts/park-shared-modules.json`.
Two fa tests compare the two copies: "shared relay and client mission definitions are identical"
(`calculator-mission.test.mjs`) and "client and relay use identical block rules"
(`calculator-lobby.test.mjs`). In CI, the park job checks out **cr main HEAD** as the sibling, so
**cr must land first**. Otherwise fa's CI compares against the old relay copy and stays red.
`node scripts/sync-park-calculator.mjs` is the existing vendoring step. After the regen it should
report exactly 1 changed file. cr's own `railway-server` park tests do not read fa's catalogue
(four of them import fa's `replica.mjs`, which does not change).

## 3. Options

### A: the generator alone is truth (regenerate both copies, fix or re-pin the six tests)
- Undoes the 28 route shortenings. That breaks the fluency rule "a hint never sends a student the
  long way and then charges them for the short one". It also invalidates `calculator-goals.mjs`,
  whose one goal phrase per route step was reviewed by the teacher in CALCULATOR_GOALS_REVIEW.md.
- Effort: high (re-derive goal phrases, re-pin the boxplot route, span and goals tests, then teacher review).
- Risk: high. It is a student-visible regression in the calculator room, made to fix a date.
- Not recommended.

### B: the committed catalogue is truth (hand-patch dates in both copies, then "fix" the generator)
- Hand-edit 50 date spots in a file marked "Do not edit", copy it to the relay, and later teach the
  generator to reproduce the committed routes.
- The generator fix B needs already exists: it is the audit pass. So B ends in the same place as C,
  just with hand edits in a generated file.
- Effort: medium. Risk: medium (a mistyped date, or a missed coverage entry versus a level date; the
  failing test would catch most of these).

### C (recommended): run the two-step pipeline as designed, sync, then pin it
- Step 1, the data fix: generator, then `--apply`, then sync to the relay. Tools produce the date-only diff.
- Step 2, the pins (section 5, a separate small change after review): one command builds the catalogue,
  and a quick-gate test catches stale dates before a schedule push leaves fa.
- Effort: about 30 minutes for the data fix, plus about 1-2 hours for the pins.
- Risk: low. The diff is dates only, verified in scratch. The relay deploy restarts the park relay
  on Railway, so push cr outside a B or E block.

## 5. Pins so this cannot recur silently (follow-up change, after review)

1. **One command builds the catalogue.** Move the audit's `shorten` pass into an importable module.
   The generator calls it before it writes, and the audit CLI keeps its report mode. Add
   `npm run build:park-catalog` (generator, then sync to the relay) and fix the catalogue header so it
   names the real pipeline. This removes the trap that produced the 11/07 misdiagnosis.
2. **Freshness test in test:park.** Refactor the generator into a `buildCatalog()` export that does
   not write. A new `apstat-park/calculator-catalog-fresh.test.mjs` asserts that the in-memory build
   equals the committed `CALCULATOR_PROBLEMS`. It catches both route drift and date drift, and its
   message names `npm run build:park-catalog`.
3. **Quick-gate date pin (the one that would have stopped ae65d549 and 084d953a).** Both schedule
   pushes ran `npm run test:quick`, but the park tests are node:test and live outside it. Add a
   small vitest file, `tests/park-catalog-dates.test.js`, to `vitest.quick.config.js`. It makes the
   same level-dates versus `curriculumCoverage(schedule)` assertion as the failing test (cheap, no
   engine replay), so a schedule change that moves a calculator lesson fails before the push.
4. **Schedule generator reminder.** At the end, `scripts/build-lesson-schedule-sy2627.mjs` prints
   "calculator lessons moved: run npm run build:park-catalog" when any catalogue date differs.
   It stays read-only toward the park.
5. **CI does not hide the next red.** Give the roster-server step `if: success() || failure()` (or
   its own job), so a park failure no longer skips the roster-server tests.
